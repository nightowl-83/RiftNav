Holo Deck
Motion Spec

A state-driven video background for the Rift Finder Holo deck. Six short clips wired to a state machine — not one long timeline with seek points. This document covers the clip graph, the Higgsfield generation brief, the playback module, and a drop-in prompt for the Claude Design canvas.

01 The decision

The intuitive approach — render one continuous video containing every state and seek to timestamps — fails on how browsers actually decode video.

Setting video.currentTime = 12.5 does not jump to that frame. The browser seeks to the nearest keyframe, then decodes forward. You land near your mark, with a decode stall and often a visible flash. Forcing a keyframe on every frame fixes accuracy but multiplies file size several times over. Either path produces exactly the jarring cut the design is trying to avoid — and every new state means re-rendering and re-cutting the whole timeline.

Approach

Model the background as a directed graph of short clips. Stills are the nodes; clips are the edges. Each clip is generated with its first and last frames locked to a shared still, so the player can hard-cut between clips and the viewer sees continuous motion.

Total asset budget for the full graph is roughly 15 seconds of video — smaller than the single-timeline approach, individually cacheable, and extendable one edge at a time.

02 State graph

Three states, six clips. The graph maps directly onto controls already in the design: skipBoot gates the boot edge, the RETARGET button drives the event self-transition, and ABORT RIFT drives the return edge.

Fig. 01 — Clip graph. Solid edges are always present; the dashed retarget edge is optional and can be deferred to a later stage.

The junction-frame rule

This is the constraint everything else depends on. Every clip's last frame must be pixel-identical to the first frame of any clip that can follow it.

  • holo-boot ends on KF-REST, which is where holo-idle begins.
  • holo-idle begins and ends on KF-REST — that is what makes it a true seamless loop rather than a hidden cut.
  • holo-engage begins on KF-REST and ends on KF-EVENT.
  • holo-return is the exact inverse.

When this holds, transitions are hard cuts with no crossfade. That matters: crossfades on generated video look mushy and read as an error rather than a move.

04 Generation brief & prompts

The graph is only buildable because Higgsfield exposes models that accept both a start frame and an end frame. Verified against the connector's model catalogue: flux_3_video (FLUX 3 Video, Black Forest Labs), wan3_0 and wan3_0_prime (Wan 3.0 / Prime) all carry start_image and end_image media roles. Any model exposing only start_image — Kling 3.0 Turbo, for instance — cannot build this graph.

Model

Wan 3.0 Prime (wan3_0_prime) at 1080p, 16:9, generate_audio: false, enable_thinking: true. It carries the first-last-frame tag and accepts durations from 2s. FLUX 3 Video also does start-plus-end frames but has a 5s minimum, which would force trimming and break the very end-frame lock the architecture depends on.

Constraint · corrected

Duration is whole seconds with a 2-second floor. The manifest in §03 reflects this. Sub-second timing is not available at generation, so anything shorter has to come from trimming — and trimming a conditioned clip discards the locked end frame, which is the one thing that cannot be given up. Design the motion to fill the whole 2 or 3 seconds instead.

Order of operations

  1. Lock the three stills

    Pull KF-REST from the existing proof-of-concept clip or Midjourney, then derive KF-EVENT and KF-VOID from it by image edit — never by fresh generation. Nothing else starts until all three are signed off: every clip is conditioned on them, so changing a still invalidates every clip that touches it.

  2. Generate each edge as a conditioned segment

    One generation per row of the manifest, supplying the manifest's start and end stills. Because the endpoints are supplied images rather than wherever the model drifts, junctions match by construction.

  3. Verify the junctions numerically

    Extract the first and last frame of every clip and diff them against the source still. Anything above a small perceptual delta gets regenerated, not colour-corrected. Do this before encoding — it is the one QA step that cannot be skipped.

How to prompt a first-and-last-frame model

This is not text-to-video prompting, and the habits transfer badly. When both endpoints are supplied as images, the images already define the subject — the prompt's only job is to describe the path between them.

Re-describing the character, the costume, the colour or the environment competes with the conditioning images and is the single most common cause of mid-clip identity drift. Every prompt below is roughly ninety percent verbs. What appearance language remains is there to hold things constant, not to introduce them.

Each prompt has four parts in this order: the camera instruction (including an explicit "static" when it does not move), the subject motion, a constancy clause naming what must not change, and the shared block below.

Constancy block — append verbatim to all six

Shared suffix
Volumetric holographic projection of a single figure, cyan and ice-blue light
on a near-black deck. Faint horizontal scanlines, soft chromatic fringing at
the silhouette edge, fine particulate drift inside the projection volume.
One continuous take — no cuts, no dissolves, no speed ramps. Locked exposure
and colour temperature: the light level on the last frame matches the first
exactly. Figure scale and screen position unchanged unless the camera
instruction states otherwise. No text, no interface elements, no captions,
no lens flare, no vignette pulse, nothing new entering frame.

The two loop clips

These are the hard ones — start and end image are the same file, and the model's instinct is either to do nothing or to wander off and come back sloppily. The phrase that does the work is "a single closed cycle": it gives the model something to animate that is guaranteed to return to origin.

holo-idle · 3s · KF-REST → KF-REST
Camera static. The figure holds its pose and does not translate, turn, or
change scale at any point in the clip. Animate only the projection itself:
a slow brightness flicker, one horizontal scanline travelling from the feet
to the head across the full three seconds, and faint particulate drift around
the silhouette. The motion is a single closed cycle — every element returns
to exactly where it started, so the final frame is identical to the first.
holo-event · 3s · KF-EVENT → KF-EVENT
Camera static. The figure holds the turned, closer pose and does not
translate, rotate, or change scale. Animate only the projection: slow
brightness flicker, one horizontal scanline travelling upward across the
full three seconds, faint particulate drift at the edges. A single closed
cycle — every element returns to its starting position, so the final frame
is identical to the first.

The transition pair

Spell out the mirrored move explicitly. The model generating holo-return has never seen holo-engage, so "the reverse of the other clip" means nothing to it — name the direction, the distance and the easing on both sides or the pair will not match.

holo-engage · 2s · KF-REST → KF-EVENT
One continuous camera move: the camera arcs to the RIGHT around the figure
and pushes in, ending closer and off-axis. Simultaneously the figure turns
from its resting three-quarter pose to face the camera directly. Smooth
ease-in-out, decelerating clearly through the final third so the move has
fully settled by the last frame. No cut, no whip pan, no motion-blur streaks.
The figure stays centred in frame throughout the arc.
holo-return · 2s · KF-EVENT → KF-REST
One continuous camera move: the camera arcs to the LEFT around the figure
and pulls back out, ending wider and on-axis. Simultaneously the figure turns
from facing the camera directly back to its resting three-quarter pose.
Smooth ease-in-out, decelerating clearly through the final third so the move
has fully settled by the last frame. No cut, no whip pan, no motion-blur
streaks. The figure stays centred in frame throughout the arc.

Boot and retarget

holo-boot · 3s · KF-VOID → KF-REST
Camera static. The projection assembles: scattered light motes gather from
the deck floor upward and coalesce into the standing figure, resolving feet
to head in one continuous bottom-up wipe over the first two seconds. The
final second is a settle — the silhouette stabilises, the flicker calms to a
steady idle, and the figure is fully formed and at rest when the clip ends.
Ease out hard into the final frame.
holo-retarget · 2s · KF-EVENT → KF-EVENT
Camera static. The figure's pose, scale and screen position are identical on
the first and last frame and do not change in between. A single bright scan
band sweeps once from the top of the figure to the bottom and leaves frame,
briefly intensifying the projection's edge glow as it passes. The glow
returns fully to its resting level before the clip ends. No other motion.

Stills: generate KF-EVENT from KF-REST, never fresh

This is the step most likely to be got wrong, and it is unrecoverable if it is. Generating KF-EVENT as a new image from a text prompt produces a different-looking hologram — close enough to seem fine in isolation, obviously wrong the moment holo-engage tries to travel between the two. Derive it by image-editing KF-REST instead, so identity is inherited rather than re-rolled.

KF-EVENT · image edit from KF-REST
Keep this exact figure — same design, proportions, costume, colour and
projection style. Re-frame closer, from roughly thirty degrees to the right
of the original camera position, with the figure turned to face the viewer
directly. Same near-black deck, same scanline density, same lighting
temperature and intensity. Change only the camera position and the figure's
facing. Do not restyle, do not redesign, do not change the palette.
KF-VOID · image edit from KF-REST
The same deck from the same camera position, with the figure removed
entirely. A faint circular projector footprint on the floor where the figure
stood, and a few stray light motes drifting above it. Same near-black ground,
same lighting temperature, same scanline density as the source.
Salvage check

The existing 8-second proof-of-concept clip was generated as one continuous shot, so its 2-second mark almost certainly does not match its loop point. Expect to regenerate against locked stills rather than recut the existing file. Its best use is as the source frame for KF-REST — pick the cleanest, most neutral standing frame in it and upscale that.

What to expect

  • Generate the two loop clips first. If the model cannot hold a figure still for three seconds and land back on its start frame, the whole architecture needs rethinking — and that is the cheapest possible place to discover it, before any transition work exists.
  • Budget three to five attempts per clip. Conditioned generation is more constrained than open text-to-video, but "returns to exactly the start" is a demanding instruction and will not land first try every time.
  • The endpoints protect the junctions, not the middle. A clip can start and end perfectly and still drift through its own midpoint. Watch the middle second of every transition specifically — it is the failure the frame-diff QA in step 3 will not catch.

05 Playback module

Two stacked <video> elements. One is visible and playing; the other is hidden and preloaded with the likely next clip. Switching means swapping which is visible — the incoming clip is already decoded, so there is no load pause.

For when to swap, use requestVideoFrameCallback() rather than the timeupdate event. timeupdate fires roughly four times a second and will overshoot the end of a clip, producing a visible stutter; requestVideoFrameCallback fires once per rendered frame. Support is 94% globally — Chrome and Edge 83+, Safari 15.4+, Firefox 132+ — so a timeupdate fallback covers the remainder.

holo-deck.js
const GRAPH = {
  boot:     { src: 'holo-boot.mp4',     loop: false, next: 'idle'  },
  idle:     { src: 'holo-idle.mp4',     loop: true                    },
  engage:   { src: 'holo-engage.mp4',   loop: false, next: 'event' },
  event:    { src: 'holo-event.mp4',    loop: true                    },
  retarget: { src: 'holo-retarget.mp4', loop: false, next: 'event' },
  ret:      { src: 'holo-return.mp4',   loop: false, next: 'idle'  },
};

// Which edge to take from a given state to reach a target state.
const ROUTE = {
  'idle→event': 'engage',
  'event→idle': 'ret',
  'event→event': 'retarget',
};

const EPS = 0.08; // seconds of slack at the loop boundary

class HoloDeck {
  constructor(mount, { skipBoot = false } = {}) {
    this.els = [this._video(mount), this._video(mount)];
    this.front = 0;
    this.state = 'idle';   // logical state, not the playing clip
    this.pending = null;
    this.mount = mount;
    this._play(skipBoot ? 'idle' : 'boot');
  }

  _video(mount) {
    const v = document.createElement('video');
    Object.assign(v, { muted: true, playsInline: true, preload: 'auto' });
    v.style.cssText = 'position:absolute;inset:0;width:100%;height:100%;' +
                      'object-fit:cover;opacity:0;';
    mount.appendChild(v);
    return v;
  }

  /* Public: ask to reach a logical state. Fires an immediate ack so the
     UI can respond in ~100ms even when the video has to wait for a
     loop boundary. */
  request(target) {
    this.mount.dispatchEvent(new CustomEvent('holo:ack', { detail: { target } }));
    const edge = ROUTE[`${this.state}→${target}`];
    if (!edge) return;
    this.state = target;
    this.pending = edge;   // consumed at the next boundary
  }

  _play(id) {
    const clip = GRAPH[id];
    const back = this.els[1 - this.front];
    back.loop = clip.loop;
    back.src = clip.src;
    back.currentTime = 0;

    const reveal = () => {
      back.style.opacity = '1';
      this.els[this.front].style.opacity = '0';
      this.front = 1 - this.front;
      this.current = id;
      this._watch(back, clip);
      if (clip.next) this._preload(clip.next);
    };

    // Reveal only once a real frame has been rendered — never on 'play'.
    back.play().then(() => {
      back.requestVideoFrameCallback
        ? back.requestVideoFrameCallback(reveal)
        : back.addEventListener('loadeddata', reveal, { once: true });
    });
  }

  _watch(v, clip) {
    const tick = (_, meta) => {
      if (this.current !== clip.srcId && v !== this.els[this.front]) return;
      const atEnd = meta.mediaTime >= v.duration - EPS;
      if (atEnd) {
        if (this.pending) { const n = this.pending; this.pending = null; return this._play(n); }
        if (!clip.loop && clip.next) return this._play(clip.next);
      }
      v.requestVideoFrameCallback(tick);
    };
    v.requestVideoFrameCallback(tick);
  }

  _preload(id) {
    const back = this.els[1 - this.front];
    if (back.src.endsWith(GRAPH[id].src)) return;
    back.src = GRAPH[id].src;
    back.load();
  }
}

Preload policy

idle is the hub, so while it loops, preload holo-engage — it is the only edge out. While event loops, holo-return is the more likely exit than holo-retarget; preload return and let retarget fetch on demand, since a 1.2s clip at 1080p arrives fast enough on any connection that can already stream the rest.

Note

The module above uses the native loop attribute for looping clips, which is simple and adequate for a hologram. Some browsers introduce a sub-frame gap on native loop. If QA sees a hitch, upgrade the loop clips to the same A/B ping-pong the transitions already use — the code path exists, it just needs the loop clip to schedule itself as its own next.

06 Latency & feel

This is the part most likely to make the finished thing feel broken, and it is not obvious until it is built.

A click during a loop cannot transition immediately. The player must reach the loop's end frame before it can cut, or the junction rule is violated and the seam shows. With an 8-second idle loop, worst case the guide ignores the user for eight seconds.

Three fixes — use all three

  • Keep loops at 3 seconds. Worst-case wait drops under 3s, average 1.5s. This is why the manifest specifies 3.0s and not 8.0s.
  • Acknowledge in the DOM, not the video. The holo:ack event fires the instant request() is called. Wire it to the card's selected state, a corner-bracket snap, or a scan pulse on the status line. The user gets feedback in ~100ms regardless of where the video is in its loop.
  • Let the aesthetic carry the seam. Flicker, scanlines and chromatic fringing mask frame discontinuity extremely well. The holoScan toggle already in the canvas is doing double duty here — it is an aesthetic choice and the technical mask that buys tolerance at every junction. Keep it on by default.
Design consequence

Because the idle pose is near-static and noisy, a cut from almost any point in the loop is close to invisible. This is a real advantage of the hologram concept over, say, a live-action or clean-3D background — the direction chosen makes the engineering easier, not harder.

07 Encoding & delivery

  • H.264 High profile in MP4 is the universal default for a desktop-first tool. Add VP9/WebM only if bandwidth becomes a measured complaint rather than an assumed one.
  • Keyframe at frame 0 of every clip — automatic, but verify. A short GOP elsewhere is unnecessary since nothing seeks.
  • muted + playsinline + autoplay. Autoplay only works muted. Any audio requires a prior user gesture.
  • A poster on every element, set to that clip's start still. There should never be a black flash — the stills already exist, so this is free.
  • Budget: ~15s at 1080p / H.264 lands around 10–14 MB total, split across six independently cacheable files.
Decide before generating

Alpha channel is a fork in the road. If the guide floats over the interface rather than filling the background, you need transparent video — and no single format covers every browser: HEVC-with-alpha for Safari, VP9-with-alpha for Chrome and Firefox, or a side-by-side RGB-plus-matte file composited in a canvas shader. That choice changes the entire asset pipeline, so settle it before the stills are locked, not after.

08 Accessibility & fallbacks

  • WCAG 2.1 SC 2.2.2 Pause, Stop, Hide (Level A) applies: this background moves automatically, runs longer than five seconds, and sits alongside other content. It needs a visible pause control, or a documented argument that the motion is essential. A "HOLO / CLASSIC" switch already exists in the design — if CLASSIC renders a static ground, that switch is the compliance mechanism. Make that explicit rather than incidental.
  • prefers-reduced-motion: reduce → skip video entirely and render the poster still. Do not merely slow it down.
  • Contrast is the real risk. Hologram backgrounds are the classic place body text fails. Treat videoDim as a token, not a taste slider, and set its floor at whatever value holds body text at 4.5:1 against the brightest frame of any clip — not the average frame, and not a screenshot of the idle pose.
  • iOS low-power mode blocks autoplay outright. The poster fallback path is not an edge case; it is a normal state on phones.
  • The video is decorative. Mark it aria-hidden. The moment the guide conveys state the interface does not also convey, it becomes content and needs a text equivalent — so keep the status line (GUIDE ONLINE / AWAITING RIFT SELECTION) authoritative and the video illustrative.

11 Build sequence

Staged so each step produces something testable and nothing is generated before it is needed.

  1. Placeholder states on the canvas

    Run the §10 prompt. No generated video at all. Proves the state model, the artboards, and the acknowledgement pattern — and gets the contrast question answered before any asset exists.

  2. Two clips, real playback

    Lock KF-REST, generate holo-boot and holo-idle, wire the playback module. Proves the boot-to-loop hand-off and the junction rule with the least possible asset spend.

  3. One transition pair

    Lock KF-EVENT, add holo-engage and holo-return. Proves the graph, and surfaces the loop-boundary latency in real use — this is where the 3-second loop decision gets validated or revised.

  4. Retarget, then fan out

    Add holo-retarget only if the RETARGET button reads as unresponsive without it. Additional camera positions only if step 3 earns them — remember the n² guard in §03.

12 Open assumptions

Pressure-test these before committing budget. Each one changes the spec materially if it turns out false.

  • The transition is a camera move, not a character performance. This spec assumes the view arcs and pushes in while the figure mostly holds. If the guide performs distinct gestures per state, clip count and generation cost multiply, and the junction rule gets much harder to satisfy.
  • Three camera positions is enough. If product wants a distinct view per rift type, revisit §03 before anything else — that is the decision with the largest cost consequence in this document.
  • The existing 8-second clip is reference, not source. Assumed unusable as cut footage. Worth ten minutes of checking before accepting the regeneration cost.
  • Background over transparent. This spec assumes a full-bleed background. Alpha compositing changes the pipeline end to end (§07).
  • This is a browser app. Everything here is HTML5 video. Electron changes little; a native or engine-based client changes almost all of §05 and §07.
  • The guide is decorative. If it ever communicates state the interface does not, §08 stops being a checklist and becomes a redesign.
